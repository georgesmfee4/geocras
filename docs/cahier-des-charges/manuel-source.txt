#0 À qui s'adresse ce manuel

Ce document est écrit pour vous, et pour personne d'autre. Là où le cahier des charges explique le produit à quelqu'un qui l'évalue, celui-ci explique la mécanique à celui qui doit la maintenir. Rien n'y est vendu ; tout y est démonté.

L'ordre suit celui d'un apprentissage réel plutôt que celui d'une table des matières logique. On commence par installer et faire tourner, parce qu'on comprend mal une architecture qu'on n'a jamais vue démarrer. On passe ensuite aux bibliothèques une par une, puis à la façon dont les morceaux se tiennent, puis aux algorithmes. Les pièges connus sont regroupés à la fin, mais ils sont aussi signalés au moment où ils peuvent frapper.

Une promesse et une réserve. La promesse : tout ce qui est écrit ici a été relu dans le code, pas reconstitué de mémoire — les versions, les constantes, les noms de fonctions et les chemins de fichiers sont ceux du dépôt. La réserve : le code bouge, ce document non. Les numéros de ligne sont donc absents partout, et les noms de fonctions présents partout : un nom se retrouve avec une recherche, un numéro de ligne mène à la mauvaise ligne dès le premier commit.

#1 Vue d'ensemble en cinq minutes

#2 Ce que le système fait, mécaniquement

Un conducteur ouvre l'application. Son téléphone capte sa position, la filtre, et la garde. Il appuie sur SOS, décrit sa panne en trois écrans, et envoie. Le serveur enregistre la demande, interroge PostgreSQL pour trouver les garages dans un rayon, les classe, et renvoie tout dans la même réponse. Le conducteur choisit un garage ; le serveur pousse la demande au propriétaire de ce garage par un canal permanent. Celui qui doit se déplacer déclare son départ, et à partir de là son téléphone émet sa position toutes les quatre secondes tant qu'il bouge. Le serveur enregistre chaque point, calcule deux durées d'arrivée et les diffuse aux deux parties. Quand ils sont à moins de cent vingt mètres l'un de l'autre, chacun confirme. La base refuse de clore la demande tant que les deux confirmations n'y sont pas. Une fois close, un crédit de fidélité est écrit, et une ligne de commission est calculée à partir de la trace du voyageur.

Tout le reste — les écrans, les tables, les bibliothèques — sert cette séquence.

#2 Les trois paquets et la règle qui les gouverne

Le dépôt est un monorepo npm workspaces. Trois paquets, et un seul sens de dépendance.

[CODE]
geocras/
├── packages/shared/     @geocras/shared     ne dépend de personne
├── apps/api/            @geocras/api        dépend de shared
└── apps/mobile/         @geocras/mobile     dépend de shared
[/CODE]

La règle est qu'aucune flèche ne remonte. Le paquet partagé ignore l'existence du serveur et du mobile ; c'est ce qui lui permet d'être la source unique de vérité sans créer de cycle. Le serveur et le mobile ne se connaissent pas non plus : ils ne communiquent que par HTTP et par le canal temps réel, et ce qu'ils échangent est décrit dans le paquet partagé.

Retenez cette conséquence pratique : **`packages/shared` doit être compilé avant que quoi que ce soit d'autre puisse démarrer**. Les deux autres paquets importent son dossier `dist/`, pas ses sources. C'est la première cause d'échec au démarrage sur une machine neuve, et le message d'erreur — « Cannot find module @geocras/shared » — ne dit pas quoi faire.

#2 Les quatre couches

[FIG] assets/01-architecture.png | Les quatre couches, leurs responsabilités et leurs dépendances externes

La couche de présentation est l'application mobile. Elle affiche, elle capte la position, elle garde l'état de l'écran. Elle ne décide rien qui touche à l'argent ou à la preuve.

Le paquet partagé n'est pas une couche au sens classique : il est traversé par les deux autres. Il porte les schémas de validation, la taxonomie des pannes, le barème de fidélité, la géométrie, le contrat du canal temps réel et le modèle de facturation.

La couche métier est le serveur. C'est lui qui valide, qui décide, qui calcule les durées d'arrivée, qui écrit le journal et qui juge la preuve d'arrivée.

La couche de données est PostgreSQL avec son extension géospatiale. Elle ne se contente pas de stocker : elle porte les règles métier qui ne doivent jamais céder, sous forme de contraintes.

#2 Étape 0 — Ce qu'il faut sur la machine

Il faut Node.js en version 22 ou plus. Le champ `engines` du `package.json` racine l'exige, et ce n'est pas décoratif : le code utilise des fonctions qui n'existent pas avant. Il faut npm 10, qui vient avec Node 22, et git.

Il faut aussi trois comptes extérieurs, tous avec un palier gratuit suffisant pour développer. Un compte Neon pour la base PostgreSQL. Un compte MapTiler pour les tuiles de carte. Un compte Expo pour construire les versions installables.

[SUB] Vérifier avant d'aller plus loin

[CODE]
node --version      # doit afficher v22.x ou plus
npm --version       # doit afficher 10.x ou plus
git --version
[/CODE]

#2 Étape 1 — Cloner et installer

[STEPS]
Cloner le dépôt et se placer à la racine.
Lancer `npm install` **à la racine**, et nulle part ailleurs.
[/STEPS]

Une seule commande installe les trois paquets. C'est le propre des workspaces npm : la racine déclare `workspaces: ["apps/*", "packages/*"]`, npm résout les dépendances de tous les paquets ensemble, met le résultat dans un unique `node_modules` racine, et relie les paquets internes entre eux par lien symbolique. Quand `apps/api` importe `@geocras/shared`, il ne télécharge rien : il suit un lien vers `packages/shared`.

L'intérêt dépasse le confort. Une version de bibliothèque partagée par deux paquets n'existe qu'une fois, ce qui empêche la situation où le serveur et le mobile valident avec deux versions différentes de la même bibliothèque de schémas — un bogue qui se manifeste par des messages d'erreur incompréhensibles et qu'on met une journée à comprendre.

[NOTE] Ne jamais lancer npm install dans un sous-dossier
Un `npm install` dans `apps/api` crée un `node_modules` local qui masque celui de la racine, casse le lien symbolique vers le paquet partagé, et installe une copie séparée des dépendances communes. Si vous l'avez fait par erreur, supprimez le `node_modules` du sous-dossier et relancez l'installation depuis la racine.
[/NOTE]

#2 Étape 2 — Compiler le paquet partagé

[CODE]
npm run build --workspace @geocras/shared
[/CODE]

C'est l'étape qu'on oublie. Elle produit `packages/shared/dist/`, que les deux autres paquets importent. Son `package.json` déclare `main: "./dist/index.js"` et `types: "./dist/index.d.ts"` : sans compilation, ces deux fichiers n'existent pas et tout import échoue.

Pendant une session de travail où vous modifiez le paquet partagé, lancez plutôt le mode veille dans un terminal à part :

[CODE]
npm run dev --workspace @geocras/shared
[/CODE]

Il recompile à chaque sauvegarde. Sans lui, une modification du barème de fidélité reste invisible du serveur jusqu'à la prochaine compilation manuelle — et vous chercherez pourquoi votre changement « ne prend pas ».

#2 Étape 3 — La base de données

[STEPS]
Créer un projet sur neon.tech, puis **une branche `dev`**. Ne jamais développer contre `main`.
Ouvrir la console SQL de cette branche et activer l'extension géospatiale : `CREATE EXTENSION IF NOT EXISTS postgis;`
Copier `apps/api/.env.example` vers `apps/api/.env`.
Coller la chaîne de connexion de la branche `dev` dans `DATABASE_URL`.
Générer les deux secrets d'authentification, puis les coller dans `JWT_ACCESS_SECRET` et `JWT_REFRESH_SECRET`.
Appliquer le schéma : `npm run db:migrate`.
Charger les données de développement : `npm run db:seed`.
[/STEPS]

[SUB] Générer les secrets

[CODE]
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
[/CODE]

Lancez cette commande **deux fois** et utilisez deux valeurs différentes. Le serveur vérifie la longueur au démarrage — trente-deux caractères au minimum — mais il ne peut pas vérifier que vous n'avez pas collé la même valeur dans les deux champs. Or si les deux secrets sont identiques, un jeton de rafraîchissement devient un jeton d'accès valide, et la durée de vie courte de l'accès ne protège plus rien.

[SUB] Ce que fait le seed, et ce qu'il vous dit

Le script insère trente garages à Yaoundé avec des positions, des services, des horaires et des notes variées. Puis il fait quelque chose d'inhabituel : il affiche le plan d'exécution de la requête de proximité.

Lisez cette sortie. Vous devez y trouver `garages_location_idx`. Si l'index géospatial n'apparaît pas, la requête centrale du produit parcourt toute la table — ce qui ne se voit pas avec trente garages, et s'effondre avec trois mille. C'est un contrôle de santé, pas un journal décoratif.

Un second jeu de données existe pour les essais de terrain :

[CODE]
npm run db:seed:ebolowa      # trois garages à Ebolowa
npm run db:seed:garagiste    # un compte propriétaire de garage
[/CODE]

Ils sont dans des scripts séparés à dessein. Yaoundé est le parc de lancement ; Ebolowa est un jeu d'essai qu'on voudra retirer. Les mélanger rendrait la suppression impossible sans trier à la main.

#2 Étape 4 — Lancer le serveur

[CODE]
npm run api
[/CODE]

La commande passe par `tsx watch`, qui exécute TypeScript directement et recharge à chaque sauvegarde. Il n'y a pas de compilation préalable en développement.

Le serveur refuse de démarrer si la configuration est incomplète. C'est volontaire : le fichier `src/config/env.ts` valide toutes les variables d'environnement avec un schéma, et lève une erreur détaillée si l'une manque ou est douteuse. Une interface de programmation qui démarre avec un secret par défaut est pire qu'une interface qui ne démarre pas — la panne est silencieuse et la faille est en production.

[SUB] Vérifier que le serveur répond

[CODE]
curl http://localhost:3000/health
curl "http://localhost:3000/garages/nearby?lat=3.848&lng=11.5021&sort=certified"
[/CODE]

La première renvoie un état et une version. La seconde renvoie les garages classés autour du centre de Yaoundé — et elle est publique, donc elle marche sans jeton. Si elle renvoie une liste, la chaîne complète serveur-base-PostGIS fonctionne.

#2 Étape 5 — Lancer le mobile

[STEPS]
Copier `apps/mobile/.env.example` vers `apps/mobile/.env`.
Créer une clé sur cloud.maptiler.com et la coller dans `EXPO_PUBLIC_MAPTILER_KEY`.
Laisser `EXPO_PUBLIC_API_URL` **vide** en développement.
Lancer `npm run mobile`.
[/STEPS]

Le troisième point demande une explication, parce qu'il est contre-intuitif. En développement, l'application tourne sur un téléphone : « localhost » y désigne le téléphone lui-même, pas votre machine. Le fichier `src/config/env.ts` récupère donc l'adresse du serveur Metro, qui est la bonne adresse dans la quasi-totalité des cas.

Le code utilise `||` et non `??` pour ce repli, et ce détail vaut d'être connu. Une chaîne vide n'est pas nullish : avec `??`, un `EXPO_PUBLIC_API_URL=` vide l'emporterait sur la déduction automatique, toutes les requêtes partiraient vers une adresse vide, et l'application afficherait « connexion impossible » sans qu'aucune variable ne paraisse mal réglée.

[TAB] Les trois variables du mobile
Variable | Rôle | En développement
`EXPO_PUBLIC_MAPTILER_KEY` | Tuiles de carte | votre clé ; vide, la carte affiche « indisponible »
`EXPO_PUBLIC_API_URL` | Adresse du serveur | laisser vide, l'IP de Metro est déduite
`EXPO_PUBLIC_SUPPORT_PHONE` | Numéro du menu Assistance | valeur par défaut suffisante
[/TAB]

[NOTE] Le préfixe EXPO_PUBLIC_ veut dire ce qu'il dit
Ces variables sont inlinées dans le bundle : elles sont lisibles par quiconque décompresse l'application. On n'y met jamais de secret. La clé MapTiler y a sa place, parce qu'elle se restreint par identifiant d'application côté fournisseur ; un secret Cloudinary n'y a rien à faire, et c'est pour cela que la signature d'envoi des photographies est produite par le serveur.
[/NOTE]

#2 Étape 6 — Le build de développement, qu'on ne peut pas éviter

C'est le point de blocage principal du projet, et il faut le comprendre une fois pour ne plus s'y perdre.

MapLibre est du code natif. Expo Go, l'application qui permet de tester un projet Expo sans rien compiler, embarque un jeu fixe de modules natifs — et MapLibre n'en fait pas partie. Dans Expo Go, l'onglet Carte reste donc vide, sans message d'erreur. Ce n'est pas un bogue à chercher : c'est la conséquence normale de l'outil employé.

La solution est un *development build* : une version installable qui contient vos modules natifs, et dans laquelle le code JavaScript continue de se recharger à chaud comme dans Expo Go.

[CODE]
npm install -g eas-cli
cd apps/mobile
eas login
eas build --profile development --platform android
[/CODE]

La compilation a lieu chez Expo, pas sur votre machine. Vous n'avez besoin ni d'Android Studio, ni d'un Mac, ni d'une chaîne de compilation locale — ce qui, pour un projet mené depuis Yaoundé, n'est pas un détail. À la fin, vous téléchargez un fichier installable, vous l'installez sur le téléphone, puis vous relancez `npm run mobile` : le build se connecte à votre serveur Metro comme le faisait Expo Go.

[SUB] Le risque à mesurer pendant ce premier build

Le fichier `app.json` active la nouvelle architecture de React Native. Le greffon Expo de MapLibre existe, mais sa compatibilité avec cette architecture n'est pas confirmée. Trois issues sont possibles et il faut les connaître d'avance.

[LIST]
La carte s'affiche aux bonnes couleurs : rien à faire, le risque est éteint.
Écran gris ou plantage au montage : repasser `newArchEnabled` à `false` dans `app.json`, reconstruire, réessayer. Le kit de développement en version 54 est la dernière à l'autoriser, c'est donc une dette avec une date de péremption.
Toujours cassé : se replier sur `react-native-maps`, en acceptant un style limité sur iOS.
[/LIST]

Profitez de ce premier build pour mesurer la fluidité : soixante images par seconde au déplacement et au zoom, avec vingt marqueurs, sur un Android de milieu de gamme. C'est le budget que le produit s'est fixé.

[SUB] Pourquoi zod, et pas une validation écrite à la main

Zod permet de déclarer une forme une seule fois et d'en tirer deux choses : un validateur exécutable et un type TypeScript. C'est ce doublet qui fait tout l'intérêt.

[CODE] Le principe, en trois lignes
const schema = z.object({ lat: z.number(), lng: z.number() });
type Coordinates = z.infer<typeof schema>;   // { lat: number; lng: number }
const result = schema.safeParse(donneesInconnues);
[/CODE]

Sans cela, il faudrait écrire le type d'un côté et le contrôle de l'autre, et les deux divergeraient. Avec un type seul, TypeScript ne protège que la compilation : à l'exécution, une réponse réseau mal formée traverse tout sans obstacle. Zod comble exactement ce trou, à la frontière du système.

Le fait qu'il vive dans le paquet partagé est le vrai gain. La même définition sert au mobile pour désactiver un bouton et au serveur pour refuser une requête. La règle est écrite une fois.

[SUB] Express 5 plutôt que 4

La version 5 apporte une chose qui change la vie du code : les erreurs levées dans un gestionnaire asynchrone sont automatiquement transmises à l'intergiciel d'erreur. En version 4, un `throw` dans une fonction `async` était silencieusement perdu, et il fallait envelopper chaque route dans un utilitaire de capture. Tout le code du projet en dépend — les routes appellent des services asynchrones et laissent remonter les erreurs.

[SUB] Kysely, et le type volontairement pénible

Kysely construit du SQL en TypeScript, avec un résultat typé. Contrairement à un ORM complet, il ne cache pas le SQL : on lit ce qui part vers la base.

Le point décisif est le géospatial. Un ORM classique ne sait pas typer une colonne `GEOGRAPHY`, et le contournement habituel consiste à la déclarer non supportée puis à passer par des requêtes brutes non typées pour toute la moitié géographique du produit — c'est-à-dire pour son cœur.

Le projet va plus loin : le type qui représente un point est fait pour être désagréable.

[CODE] src/db/types.ts, l'idée
// En écriture : n'accepte qu'un fragment SQL, donc on passe forcément
// par pointFromLatLng().
// En lecture  : rend une chaîne binaire inexploitable, donc on est forcé
// de projeter ST_Y et ST_X explicitement.
[/CODE]

C'est pénible à l'usage, et c'est le but. On ne peut pas se tromper par distraction, et l'erreur classique — écrire une latitude là où on attend une longitude — devient impossible à commettre en silence.

[SUB] Socket.io plutôt que WebSocket brut

Trois raisons, dans l'ordre d'importance pour ce produit précis.

D'abord le repli de transport. Quand la connexion permanente ne s'établit pas — réseau filtrant, proxy, 2G capricieuse — Socket.io bascule tout seul sur une technique plus tolérante. C'est exactement ce qui sauve une session de suivi au Cameroun, et c'est ce qu'il faudrait réécrire à la main avec un WebSocket brut.

Ensuite la reconnexion, avec temporisation croissante, gérée sans code de notre part.

Enfin les salles, qui donnent gratuitement le découpage dont le produit a besoin : une salle par demande d'assistance, et une salle par compte utilisateur.

[SUB] Le routage par fichiers, en une phrase

Avec `expo-router`, l'arborescence du dossier `app/` **est** la navigation. Un fichier devient un écran, un dossier devient un groupe, et les parenthèses créent un groupe qui n'apparaît pas dans l'URL.

[CODE] Ce que la structure signifie
app/index.tsx                      → l'écran d'ouverture (splash)
app/(drawer)/_layout.tsx           → le tiroir latéral englobe tout ce qui suit
app/(drawer)/(tabs)/_layout.tsx    → la barre d'onglets, à l'intérieur du tiroir
app/(drawer)/(tabs)/carte.tsx      → l'onglet Carte
app/garage/[id].tsx                → fiche d'un garage, id dynamique
app/suivi/[requestId].tsx          → écran de suivi
[/CODE]

Les fichiers `_layout.tsx` sont la clé : ils décrivent ce qui **entoure** les écrans d'un niveau. C'est là que vivent les fournisseurs de contexte, et l'ordre dans lequel ils s'imbriquent a des conséquences réelles, détaillées au chapitre suivant.

[NOTE] Pourquoi deux familles de polices chargées en même temps
La refonte typographique remplace Inter par IBM Plex écran par écran. Pendant la bascule, les deux familles sont chargées : un écran non repris demande encore une variante Inter, et retirer la famille avant la fin de la passe le ferait tomber en police système sans qu'aucune erreur ne le signale. Inter partira quand le dernier écran sera repris.
[/NOTE]

#2 Les fournisseurs, et pourquoi leur ordre compte

Le fichier `app/_layout.tsx` empile les fournisseurs de contexte. Cet ordre n'est pas arbitraire : chaque niveau peut consommer ce que les niveaux au-dessus fournissent, jamais l'inverse.

[CODE] L'imbrication, de l'extérieur vers l'intérieur
SafeAreaProvider          les marges système, dont tout dépend
  QueryClientProvider     le cache réseau
    ThemeProvider         thème clair/sombre, jetons de couleur
      I18nProvider        langue et libellés
        AuthProvider      session et jetons — a besoin du cache réseau
          LocationProvider position — a besoin de la session pour émettre
            Stack         les écrans
[/CODE]

Deux conséquences pratiques. Le cache réseau est au-dessus de la session parce que la connexion est elle-même une requête réseau : l'inverse créerait une dépendance circulaire. Et la position est en dessous de la session parce qu'émettre une position exige d'être authentifié — le fournisseur de position interroge la session pour savoir s'il doit émettre.

Si vous ajoutez un fournisseur, posez-vous une seule question : de quoi a-t-il besoin ? Il se place en dessous de ce qu'il consomme.

#2 Le trajet complet d'une donnée

Suivons un seul geste — l'appui sur SOS — à travers toutes les couches. C'est l'exercice qui fait le plus pour la compréhension d'un système.

[STEPS]
**L'écran** `app/sos/declarer.tsx` collecte les réponses. Il ne fait aucun appel réseau lui-même.
**Le contrat** `packages/shared/src/contracts/requests.ts` valide la forme localement. Le bouton « Continuer » reste inerte tant que le schéma refuse. La règle qui exige un libellé libre pour un véhicule de catégorie ouverte vit ici, et nulle part ailleurs.
**Le hook** `src/api/hooks.ts` expose `useCreateRequest()`. C'est une mutation de la bibliothèque de cache : elle gère l'état d'envoi, le réessai et l'invalidation de ce qui devient périmé.
**Le client** `src/api/client.ts` ajoute le jeton d'accès, sérialise, et lance la requête. Aucun composant n'appelle `fetch` directement — c'est une règle du projet, et c'est ce qui a rendu le mode dégradé implémentable.
**La route** `apps/api/src/modules/requests/requests.routes.ts` reçoit. L'intergiciel `validateBody` applique **le même schéma** qu'à l'étape 2. Un client modifié ne passe pas.
**Le service** `requests.service.ts` décide : il vérifie qu'aucune demande n'est active, écrit la demande, inscrit l'événement fondateur au journal avec le mode de service, puis appelle la recherche de garages.
**L'accès aux données** `garages.repo.ts` construit la requête de proximité en SQL typé, avec le filtre géospatial avant le tri.
**La base** applique ses contraintes. Si le code se trompe — un véhicule immobilisé avec le mode « je vais au garage » — la ligne est refusée ici, dernier rempart.
**La réponse** remonte : la demande et les garages classés, dans un seul aller-retour.
**Le canal temps réel** `realtime/io.ts` pousse la file de travail au propriétaire du garage, si un garage a été retenu.
**Le cache** côté mobile enregistre la réponse. L'écran de résultats la lit sans nouvel appel.
[/STEPS]

Onze étapes, et une seule règle métier écrite une seule fois — appliquée deux fois, à l'étape 2 et à l'étape 5, parce que les deux extrémités importent le même fichier.

#2 Le bus interne du serveur

Un détail d'architecture qui évite un enchevêtrement : les services métier ne connaissent pas le canal temps réel.

Quand `requests.service.ts` fait avancer une demande, il ne parle pas à Socket.io. Il publie sur un émetteur interne, `realtime/bus.ts`. C'est `realtime/io.ts` qui écoute ce bus et traduit en émissions vers les salles concernées.

L'intérêt est net. Les services restent testables sans démarrer de serveur de socket. Et le jour où un second canal de diffusion apparaît — notifications poussées, journal d'audit externe — il s'abonne au même bus sans qu'aucun service ne change.

#2 La distance : la formule de haversine

Deux points sur une sphère, une distance en mètres. C'est la brique sur laquelle tout le reste repose.

[CODE] packages/shared/src/geo.ts
const EARTH_RADIUS_M = 6_371_008.8;

h = sin²(Δφ/2) + sin²(Δλ/2) · cos φ₁ · cos φ₂
d = 2 R · asin( min(1, √h) )
[/CODE]

Trois choses sont à comprendre.

Le rayon employé, 6 371 008,8 mètres, est le rayon moyen de la Terre au sens de l'Union astronomique internationale. À l'échelle d'une ville, choisir un autre rayon plausible change le résultat de quelques mètres — c'est-à-dire moins que l'imprécision du récepteur.

La formule est celle de haversine et non la loi sphérique des cosinus, qui est plus simple mais perd sa précision sur les courtes distances à cause d'arrondis en virgule flottante. Or les courtes distances sont exactement le cas d'usage : on mesure des centaines de mètres, pas des continents.

Le `min(1, …)` avant l'arcsinus n'est pas une coquetterie. Pour deux points identiques ou presque, l'accumulation d'erreurs d'arrondi peut produire une valeur très légèrement supérieure à un, et `asin` d'un nombre supérieur à un rend `NaN`. Ce `NaN` se propagerait ensuite dans la durée estimée, dans le cadrage de la caméra, et dans la preuve d'arrivée — sans qu'aucune erreur ne soit levée. Une ligne de garde contre un mode de panne silencieux.

[NOTE] Haversine côté client, PostGIS côté serveur
Le serveur n'utilise pas cette fonction pour la recherche de proximité : il emploie `ST_DWithin` et `ST_Distance` sur des colonnes de type `GEOGRAPHY`, qui tiennent compte de l'ellipsoïde et surtout consomment l'index géospatial. Haversine sert là où il n'y a pas de base à interroger : sur le téléphone, et dans le calcul de la preuve d'arrivée à partir d'une trace déjà chargée en mémoire.
[/NOTE]

#2 La durée estimée, et pourquoi elle est marquée provisoire

[CODE] packages/shared/src/geo.ts
ETA_CALIBRATION = {
  detourFactor:    1.35,   distance routière / distance à vol d'oiseau
  urbanSpeedKmh:   22,     vitesse en tissu urbain dense
  walkingSpeedKmh: 4.5,
}

estimateEtaMinutes(d, mode) = max(1, round( d × 1,35 / 1000 / v × 60 ))
[/CODE]

Le facteur de détour est l'aveu d'une approximation. Une distance à vol d'oiseau n'est pas une distance parcourue : il faut suivre des rues, contourner des îlots, respecter des sens interdits. Le rapport observé entre les deux, dans un tissu urbain dense et peu maillé, tourne autour de 1,35. Cette valeur est une calibration pour Yaoundé, à réviser sur les données réelles de la table des relevés de position.

La vitesse de vingt-deux kilomètres par heure peut sembler basse. Elle inclut les arrêts, les carrefours et la circulation — c'est une vitesse moyenne de trajet, pas une vitesse de roulage.

Le `max(1, …)` évite d'annoncer « arrive dans 0 minute », qui se lit comme un défaut d'affichage plutôt que comme une bonne nouvelle.

Cette fonction est explicitement transitoire. Le fichier porte un avertissement en tête, et l'interface marque la valeur comme provisoire. La cible est un serveur de routage OSRM auto-hébergé, désigné par la variable `OSRM_URL` — et rien d'autre ne bougera le jour de la bascule.

[NOTE] Le défaut d'OSRM_URL est un serveur public de démonstration
Il dépanne en développement, mais sa politique d'usage interdit la production : aucune garantie de disponibilité, quota partagé, et chaque requête envoie à un tiers la position d'un garagiste et le lieu d'une panne. C'est une variable à changer avant toute mise en service réelle.
[/NOTE]

#2 Le lissage de la vitesse : la moyenne mobile exponentielle

[CODE] packages/shared/src/geo.ts
SPEED_SMOOTHING_ALPHA = 0.3

smoothSpeed(précédent, échantillon) =
  précédent === null  ?  échantillon
                      :  0,3 × échantillon + 0,7 × précédent
[/CODE]

Le principe est simple : chaque nouvelle mesure ne compte que pour trois dixièmes, les sept dixièmes restants venant de l'historique. La valeur affichée bouge donc lentement, même quand la mesure saute.

Le choix de trois dixièmes est un arbitrage. Plus haut, la valeur suit mieux les accélérations réelles mais tremble ; plus bas, elle devient très stable mais met plusieurs relevés à réagir à un vrai changement d'allure. À une émission toutes les quatre secondes, 0,3 donne une réponse en une quinzaine de secondes — assez vif pour un usage routier, assez calme pour que le chiffre ne clignote pas.

Pourquoi lisser ? Parce que la durée d'arrivée se calcule à partir de la vitesse, et qu'une vitesse brute fait sauter le chiffre d'un relevé à l'autre. Un temps d'arrivée qui passe de huit à quinze puis à six minutes est plus anxiogène qu'aucun temps du tout : l'utilisateur cesse de le croire, et avec lui il cesse de croire le reste de l'écran.

#2 Le rejet des sauts implausibles

[CODE] packages/shared/src/geo.ts
MAX_PLAUSIBLE_SPEED_MPS = 150 / 3,6      ≈ 41,7 m/s

isPlausibleMove(de, vers, Δt) =
  Δt > 0  ET  haversine(de, vers) / Δt ≤ 41,7
[/CODE]

Le raisonnement est physique. En ville camerounaise, un déplacement impliquant plus de cent cinquante kilomètres par heure entre deux relevés n'est pas une voiture : c'est une dérive du récepteur, typiquement causée par un signal réfléchi entre deux immeubles ou par une position calculée sur trop peu de satellites.

Le seuil est volontairement généreux. Un seuil serré — quatre-vingts kilomètres par heure, par exemple — rejetterait des déplacements réels sur les axes rapides, et l'utilisateur verrait son point rester collé. Mieux vaut laisser passer une aberration modérée que censurer un mouvement authentique.

Le test `Δt > 0` traite un cas réel : un horodatage identique ou antérieur au précédent signale un relevé rejoué par le système d'exploitation. Sans cette garde, on diviserait par zéro.

#2 Le filtre de position, en quatre passes

La classe `PositionFilter` dans `apps/mobile/src/location/filter.ts` assemble les briques précédentes en une chaîne de décision. Chaque relevé du récepteur y passe.

[STEPS]
**Précision.** Au-delà de deux cents mètres, la mesure est écartée. Le seuil est généreux à dessein : masquer un point à ±150 m laisserait l'utilisateur sans position du tout, alors que ±150 m reste une information exploitable pour chercher un garage.
**Horodatage.** Un écart nul ou négatif signale un relevé rejoué. On garde le précédent.
**Plausibilité.** Le déplacement est confronté au seuil de cent cinquante kilomètres par heure. Rejeté s'il le dépasse.
**Lissage.** La vitesse retenue est la moyenne mobile exponentielle de la précédente et de l'échantillon.
[/STEPS]

Une décision explicite mérite d'être soulignée : **on ne filtre pas sur la précision seule**. Un point à quarante mètres près reste la meilleure information disponible quand c'est tout ce qu'on a. Le produit affiche d'ailleurs cette précision réelle plutôt qu'une valeur rassurante — un badge « ±5 m » qui mentirait détruirait la confiance dans tout le reste de l'écran.

#2 Le cadrage de la caméra

Après avoir des points, il faut décider ce que la caméra montre. Deux fonctions, dans `apps/mobile/src/map/bounds.ts`.

[CODE]
boundsOf(points)  →  [ouest, sud, est, nord]  |  null
MIN_SPAN_DEGREES  =  0,0004                      ≈ 40 mètres
isDegenerate(b)   →  vrai si les DEUX côtés sont sous le seuil
[/CODE]

L'ordre des quatre nombres suit celui qu'attend MapLibre, et c'est délibéré : aucun appelant n'a à réarranger quatre valeurs. C'est exactement le genre d'inversion latitude/longitude qui envoie une caméra au large du golfe de Guinée sans qu'aucune erreur ne soit levée.

Les points non finis sont **écartés** plutôt que propagés. Un seul `NaN` dans une géométrie suffirait à rendre les quatre bornes indéfinies, et la fonction de cadrage échouerait alors en silence : la caméra ne bougerait pas, et rien à l'écran ne dirait pourquoi.

Le test de dégénérescence traite un cas qui arrive à chaque intervention. Quand le dépanneur atteint la panne, son point de départ et sa destination se confondent. Cadrer un rectangle de hauteur nulle envoie la caméra en butée de zoom, et l'écran n'affiche plus qu'un carré de bitume. La condition exige que les **deux** côtés soient sous le seuil : un trajet parfaitement nord-sud a une largeur nulle et reste parfaitement cadrable.

#2 Les cercles de précision

[CODE] apps/mobile/src/map/circle.ts
metersPerDegreeLat = 111 320
metersPerDegreeLng = 111 320 × cos(latitude)

pour i de 0 à 48 :
  angle = i/48 × 2π
  point = [ lng + r·cos(angle)/metersPerDegreeLng,
            lat + r·sin(angle)/metersPerDegreeLat ]
[/CODE]

Deux points de conception importent ici.

C'est un **polygone géographique**, pas un cercle d'écran. Le rayon représente une distance sur le terrain — la précision du récepteur, la zone d'incertitude d'une position masquée — et doit donc grandir quand on dézoome. Un cercle à rayon fixe en pixels afficherait une précision constante à tous les niveaux de zoom, c'est-à-dire exactement le contraire de ce que ces cercles servent à dire.

La projection est plate, et c'est assumé. Le cosinus de la latitude corrige le rétrécissement des degrés de longitude quand on s'éloigne de l'équateur. À l'échelle du kilomètre et sous l'équateur, l'écart avec une géodésique exacte est de l'ordre du centimètre. Ce qu'on dessine est une incertitude, pas un cadastre.

Quarante-huit segments donnent un cercle visuellement lisse sans alourdir la géométrie. En dessous d'une vingtaine, le polygone se voit.

#2 Le décodage des itinéraires

OSRM peut rendre sa géométrie en GeoJSON, mais le projet demande du **polyline6**. La raison est un facteur dix : un trajet urbain d'un kilomètre pèse environ trois cents octets encodé, contre deux à trois kilooctets en GeoJSON, pour un tracé identique. Sur un forfait de données compté, la différence n'est pas théorique.

L'algorithme est celui de Google, connu sous le nom d'*encoded polyline algorithm format*. Il repose sur trois idées empilées.

[STEPS]
**Différences successives.** On n'encode pas les coordonnées absolues mais l'écart avec le point précédent. Des écarts sont de petits nombres, donc courts à écrire.
**Zig-zag.** Un entier signé est transformé en entier non signé en repliant les négatifs sur les impairs : le bit de poids faible porte le signe. Cela évite de gaspiller les bits de poids fort pour représenter un signe.
**Groupes de cinq bits.** Le nombre est découpé en tranches de cinq bits, chacune écrite comme un caractère imprimable. Le sixième bit signale qu'une tranche suit.
[/STEPS]

Le suffixe « 6 » désigne le facteur d'échelle : un million au lieu de cent mille, soit une précision de dix centimètres au lieu d'un mètre.

Un piège mérite le détour, parce qu'il est classique et silencieux. **OSRM encode la latitude d'abord**, alors que GeoJSON et MapLibre attendent la longitude d'abord. L'inversion est faite dans `decodePolyline6`, au seul endroit du code qui connaît la convention d'OSRM. La laisser fuir plus loin produirait une polyligne au milieu de l'océan Atlantique — sans aucune erreur levée, puisque les deux nombres sont valides.

Notez aussi que le décodage a lieu **sur le serveur**. Le mobile reçoit des coordonnées prêtes à peindre. C'est notre serveur qui absorbe le format d'OSRM, ce qui permettra de changer de moteur de routage sans toucher à l'application.

#2 Le style de carte

Le projet ne charge pas un style tout fait. Il consomme les **tuiles vectorielles** de MapTiler et déclare ses propres couches, dans `apps/mobile/src/map/style.ts`.

C'est la seule façon d'obtenir exactement le fond `#EFEBE2` et les routes `#FEFBF0` sur casing `#E2DDD1` des maquettes : un style tiers impose ses couleurs, et l'identité visuelle est déclarée non négociable.

[CODE] L'ordre des couches, du fond vers l'avant
background            l'aplat crème
landcover-vegetation  végétation
park                  parcs
water, waterway       eau et cours d'eau
building              bâti
road-*-casing         le contour sombre des routes (mineures, secondaires, majeures)
road-*                le remplissage clair, par-dessus le casing
road-label            noms de rues
place-label           quartiers
locality-label        localités
[/CODE]

La technique du **casing** est ce qui donne aux routes leur aspect dessiné : on peint d'abord un trait large et sombre, puis un trait plus fin et clair par-dessus. La différence de largeur crée un liseré qui sépare la route du fond. C'est pourquoi chaque niveau de route apparaît deux fois dans la liste, et pourquoi tous les casings viennent avant tous les remplissages — sinon un casing de route majeure recouvrirait le remplissage d'une route mineure à son croisement.

[CODE] La largeur de route, interpolée par zoom
['interpolate', ['exponential', 1.5], ['zoom'], z1, w1, z2, w2, …]
[/CODE]

L'interpolation exponentielle de base 1,5 fait grossir la route plus vite aux zooms élevés qu'une interpolation linéaire. C'est ce qui correspond à la perception : en s'approchant, on s'attend à ce que la rue occupe proportionnellement plus de place.

Deux absences sont volontaires. **Aucune couche de points d'intérêt** : le cahier des charges interdit les repères parasites, et les seuls objets qui doivent capter l'œil sont les marqueurs de garages. Et aucune couleur vive en dehors du rouge de l'identité.

[NOTE] Un écart connu sur les polices de carte
Les glyphes vectoriels d'Inter ne sont pas disponibles chez MapTiler. Les étiquettes de rues utilisent donc Noto Sans, alors que l'interface est en IBM Plex. Pour aligner les deux, il faudra téléverser la police dans MapTiler Cloud et changer l'URL `glyphs`. Sans conséquence sur la règle « chiffres en mono », qui porte sur l'interface et non sur le rendu de la carte.
[/NOTE]

#2 La recherche de proximité, côté base

C'est la requête centrale du produit, et elle repose sur trois mécanismes de PostgreSQL.

[SUB] Le type géographique

Les positions sont stockées en `GEOGRAPHY(POINT, 4326)` et non en `GEOMETRY`. La différence est décisive : le type géographique rend directement des mètres en tenant compte de la courbure terrestre, sans conversion manuelle ni choix de projection à justifier. Sur un produit dont la fonction centrale est une distance en mètres, c'est le type qui dit la vérité par défaut.

Le nombre 4326 désigne le système de référence WGS 84, celui des récepteurs GPS.

[SUB] L'index GIST, et pourquoi le filtre doit précéder le tri

[CODE]
CREATE INDEX garages_location_idx ON garages USING GIST (location);
CREATE INDEX garages_certified_location_idx ON garages USING GIST (location)
  WHERE is_active AND certified;
CREATE INDEX garages_services_idx ON garages USING GIN (services);
[/CODE]

Un index GIST — *Generalized Search Tree* — organise l'espace en rectangles englobants emboîtés. Interroger « quels points sont à moins de dix kilomètres d'ici » revient à descendre l'arbre en éliminant des branches entières, au lieu de mesurer la distance de chaque ligne.

Encore faut-il que la requête le lui permette, et c'est là l'invariant à ne jamais casser :

[CODE] Ce qui consomme l'index
WHERE ST_DWithin(g.location, $origine, $rayon)      ← filtre, indexable
ORDER BY distance_m                                  ← tri, sur le résultat filtré

Ce qui ne le consomme pas
ORDER BY ST_Distance(g.location, $origine)          ← calcule pour TOUTE la table
[/CODE]

La seconde forme est correcte : elle rend les bons garages dans le bon ordre. Elle parcourt simplement la table entière, ce qui ne se voit pas avec trente lignes et s'effondre avec trois mille. Un test automatisé vérifie le plan d'exécution pour cette raison précise — c'est une exigence non fonctionnelle transformée en test, et la seule manière d'empêcher une régression de performance de passer inaperçue pendant six mois.

Le second index est **partiel** : il ne couvre que les garages actifs et certifiés. Il est plus petit, donc plus rapide, et sert le tri par certification.

Le troisième est un index **GIN**, adapté aux tableaux : il accélère la question « ce garage offre-t-il tel service ? ».

[SUB] Le rang calculé en SQL

[CODE]
ROW_NUMBER() OVER (ORDER BY
  CASE WHEN $sort = 'certified' THEN NOT certified END ASC,
  CASE WHEN $sort = 'rating'    THEN score_note     END DESC,
  distance_m ASC,
  id ASC
)
[/CODE]

L'astuce repose sur une propriété du langage : dans une branche inactive, l'expression conditionnelle vaut la valeur nulle **pour toutes les lignes**. Elle ne discrimine donc rien, et le tri retombe sur la clé suivante.

Le résultat est qu'un seul plan de requête couvre les trois tris. On ne concatène pas de SQL selon le tri demandé — donc il n'existe aucune surface d'injection de ce côté.

La dernière clé, l'identifiant, garantit un ordre **total**. Sans elle, deux garages à distance égale pourraient s'échanger leurs rangs entre deux requêtes identiques, et les marqueurs se renumérotteraient sans raison visible.

[SUB] La note bayésienne

[CODE]
score_note = n/(n+20) × note  +  20/(n+20) × 3,8

n     nombre d'avis du garage
20    seuil à partir duquel la note propre pèse pleinement
3,8   note moyenne de référence
[/CODE]

Une moyenne simple laisserait un garage noté 5,0 sur deux avis complaisants devancer un garage noté 4,6 sur cent vingt-huit avis — exactement ce qu'un tri « mieux noté » ne doit pas faire.

La formule mélange la note observée avec une note de référence, en donnant d'autant plus de poids à la note observée que les avis sont nombreux. Avec deux avis, la note compte pour un onzième et la référence pour dix onzièmes. Avec cent vingt-huit avis, la note compte pour près de neuf dixièmes.

La note affichée sur la fiche du garage reste la note brute. La note pondérée sert à trier, pas à informer : elle serait incompréhensible pour un utilisateur.

#2 La géométrie du service et la preuve d'arrivée

[FIG] assets/09-modes-service.png | Les deux modes de service, et la fonction unique qui les traduit en géométrie

Un dépannage se déroule dans deux sens. Ou bien le garagiste vient, ou bien le client conduit jusqu'à l'atelier. Toute la difficulté est que la facturation repose sur la trace de celui qui s'est déplacé — et que ce n'est pas la même personne selon le cas.

[CODE] packages/shared/src/billing.ts
serviceGeometry('on_site',   { origin, garageLocation })
  → { traveller: 'garage',  destination: origin }

serviceGeometry('at_garage', { origin, garageLocation })
  → { traveller: 'client',  destination: garageLocation }
[/CODE]

Tout ce qui a besoin de savoir quelle trace lire ou vers quoi mesurer passe par cette fonction : la preuve d'arrivée, le registre des commissions, l'itinéraire affiché. Un test de mode recopié dans trois modules finit toujours par en avoir un de retard — et une preuve mesurée vers le mauvais point ne plante pas, elle rend simplement « aucune preuve » sur des dépannages parfaitement réels.

[SUB] Les trois signaux de la preuve

[CODE] Seuils de ARRIVAL_PROOF
radiusMeters      150      distance sous laquelle on considère être arrivé
minDwellSeconds   240      durée minimale entre l'arrivée et la fin
minTravelMeters   200      distance minimale réellement parcourue
[/CODE]

[STEPS]
**`settled`** — le dernier point de la fenêtre est-il à moins de cent cinquante mètres de la destination ?
**`travelledMeters`** — le trajet a-t-il une longueur réelle, calculée par `pathLengthMeters` qui somme les haversines successives ?
**`dwellSeconds`** — la demande a-t-elle vécu assez longtemps après l'arrivée ?
[/STEPS]

Le premier signal tire parti d'une contrainte qui ressemblait à un défaut. Pour économiser les données, le téléphone n'émet un point qu'au-delà de quinze mètres parcourus : un véhicule à l'arrêt cesse donc complètement d'émettre. C'est en réalité le signal le plus fiable dont on dispose — une trace qui **s'arrête** au lieu de s'éloigner est exactement la signature d'une arrivée, là où un simple passage devant laisse des points qui continuent.

[TAB] Les quatre niveaux rendus
Niveau | Ce qu'il établit | Facturable
`none` | Aucune trace n'établit un déplacement | Non
`weak` | Trajet trop court, ou intervention trop brève | Non
`trail` | La trace établit le déplacement | Oui
`mutual` | La trace l'établit **et** les deux parties en conviennent | Oui
[/TAB]

Un point contre-intuitif à retenir : la double confirmation d'arrivée ne **crée** aucun droit à facturation, elle hisse d'un cran une preuve déjà acquise par la trace. Le raisonnement est simple — dès qu'une confirmation conditionnerait la facture, le débiteur aurait intérêt à la retenir.

La **fenêtre de lecture** est l'intervalle entre le départ déclaré et la fin connue de la demande. Tout relevé antérieur est ignoré. C'est pourquoi la transition de mise en route appartient exclusivement à celui qui se déplace, et pourquoi le serveur le vérifie : un garagiste qui poserait cet horodatage sur une demande où le client conduit démarrerait le chronomètre de quelqu'un d'autre — au mieux trop tôt, au pire après l'arrivée, ce qui effacerait la trace entière d'un trajet réel.

#2 Le squelette d'Express

Le fichier `app.ts` assemble l'application, et son ordre est significatif : un intergiciel ne voit que ce que les précédents ont laissé passer.

[CODE] L'ordre de montage, et ce qu'il implique
app.set('trust proxy', 1)     ← AVANT tout : sinon l'IP réelle est perdue
helmet()                       en-têtes de sécurité
cors({ origin: … })            origines navigateur
express.json({ limit: '256kb' })  corps JSON, taille bornée
pinoHttp()                     journalisation (sauf en test)
GET /health                    sonde, avant l'authentification
/auth  /garages  /requests  /me  /driving  /uploads
notFoundHandler                404 au format maison
errorHandler                   DERNIER : il capte ce qui a été levé
[/CODE]

Le réglage `trust proxy` mérite une explication, parce qu'il est facile à oublier et coûteux. Derrière un hébergeur, l'adresse réelle du client se trouve dans un en-tête `X-Forwarded-For`, pas dans la connexion elle-même. Sans ce réglage, la limitation de débit voit une seule adresse — celle du proxy — et bloquerait donc tous les utilisateurs d'un coup au premier pic de trafic.

La limite de deux cent cinquante-six kilooctets sur le corps JSON est une protection : aucune requête légitime du produit n'approche cette taille, puisque les photographies ne passent pas par le serveur.

Le gestionnaire d'erreur est monté en dernier, et c'est une règle d'Express : il reçoit ce que les couches précédentes ont levé. Le monter plus haut le rendrait inerte.

#2 Les trois barrières de validation

C'est le motif le plus important à comprendre du côté serveur. La même règle est appliquée à trois niveaux, et les trois sont utiles.

[TAB] Les trois barrières, et ce que chacune protège
Barrière | Où | Ce qu'elle protège
Interface | l'écran désactive le bouton | l'utilisateur, d'une erreur
Contrat | le schéma partagé refuse la requête | le serveur, d'un client modifié ou d'une version ancienne
Base | la contrainte SQL refuse la ligne | nous-mêmes, d'un futur script d'import ou d'une reprise de données
[/TAB]

La troisième est celle qu'on est tenté de sauter, et c'est la seule qui survive au temps. Une vérification écrite dans un service est vraie tant que tous les appelants passent par ce service ; elle cesse de l'être au troisième point d'entrée ajouté six mois plus tard par quelqu'un qui ignore la règle. Une contrainte inscrite dans le schéma reste vraie même quand le code se trompe.

C'est la discipline appliquée à toutes les règles qui touchent à l'argent ou à la preuve : la double confirmation d'arrivée, l'idempotence des crédits, l'unicité d'un garage par compte, l'interdiction du mode « je vais au garage » pour un véhicule immobilisé.

#2 L'authentification

[CODE] Le mécanisme, en cinq points
Jeton d'accès        JWT signé, durée courte (15 min par défaut)
Jeton de rafraîch.   chaîne opaque aléatoire, 30 jours
En base              seule l'EMPREINTE du jeton de rafraîchissement
Rotation             chaque usage produit une nouvelle paire et révoque l'ancienne
Mots de passe        bcrypt, 12 tours par défaut
[/CODE]

Le jeton d'accès est un JWT : il porte l'identité et se vérifie par signature, sans interroger la base. C'est ce qui permet à chaque requête de coûter zéro lecture pour l'authentification.

Le jeton de rafraîchissement est l'inverse : il n'est pas un JWT mais une chaîne opaque, et il est stocké en base — mais seulement sous forme d'empreinte. Une fuite de la table ne donne donc aucune session utilisable, puisqu'on ne peut pas remonter de l'empreinte au jeton.

La rotation à chaque usage est ce qui limite les dégâts d'un vol. Un jeton dérobé et utilisé une fois est immédiatement révoqué ; le vol se détecte parce que le propriétaire légitime se retrouve déconnecté.

Le nombre de tours de bcrypt est réglable entre dix et quinze, avec douze par défaut. C'est un arbitrage entre coût de calcul et résistance : chaque tour double le temps de hachage. Douze tours représentent quelques centaines de millisecondes sur un serveur modeste — assez pour rendre une attaque par dictionnaire coûteuse, assez peu pour ne pas gêner une connexion.

#2 Le canal temps réel, en détail

[CODE] Les deux types de salles
request:<uuid>   une salle par demande d'assistance
user:<uuid>      une salle par compte, rejointe dès la connexion
[/CODE]

La salle par demande est l'évidente : le client et le garagiste y échangent positions et durées d'arrivée.

La salle par compte règle un problème que les salles par demande ne peuvent pas résoudre. Au moment où un SOS est adressé à un garagiste, celui-ci **ne connaît pas encore cette demande** : il n'a donc rejoint aucune salle, et le seul canal capable de le prévenir est celui qui le désigne lui-même. C'est aussi ce qui tient plusieurs appareils du même garage d'accord : l'atelier accepte sur la tablette, le téléphone du dépanneur voit la file changer.

[SUB] L'authentification du socket

Une connexion n'est pas authentifiée par le fait d'exister. À l'ouverture, le socket présente le jeton d'accès ; le serveur le vérifie et attache l'identité au socket. Puis, à chaque demande de rejoindre une salle, il vérifie **l'appartenance à la demande** — être authentifié ne suffit pas, il faut être partie à cette intervention précise.

[SUB] Le rejeu après coupure

C'est le mécanisme qui rend le suivi robuste, et il repose entièrement sur une propriété du journal : `request_events` est en **ajout seul** et chaque événement porte un numéro de séquence unique au sein de sa demande.

[STEPS]
Le client garde en mémoire le dernier numéro reçu.
Quand la connexion tombe, il bascule sur une interrogation périodique de la route d'état — la même route, exactement, que celle du premier chargement.
Au retour du réseau, il se réannonce en transmettant son dernier numéro.
Le serveur lit tous les événements postérieurs et les lui rejoue dans l'ordre.
[/STEPS]

L'effet secondaire est précieux : le mode dégradé et le premier chargement empruntent le même chemin de code. Il n'existe donc pas de branche rarement exécutée, donc rarement testée, qui ne fonctionnerait que le jour de la coupure.

#2 Le format des erreurs

[CODE]
{ "error": { "code": "REQUEST_ALREADY_ACTIVE",
             "message": "…",
             "fields": { … } } }
[/CODE]

Le mobile traduit sur le **code**, jamais sur le message. La conséquence pratique est qu'on peut réécrire tous les messages du serveur sans casser un seul client, et qu'on peut afficher un texte différent selon la langue sans que le serveur ait à la connaître.

#2 Ajouter une migration

[STEPS]
Créer `apps/api/migrations/00NN_ce_que_ca_fait.sql`, en incrémentant le numéro.
Écrire du SQL **idempotent** autant que possible : `IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS` avant `ADD CONSTRAINT`.
Documenter en tête du fichier **pourquoi**, pas seulement quoi. Les migrations existantes le font toutes, et c'est ce qui rend le schéma relisible un an plus tard.
Mettre à jour `src/db/types.ts` : Kysely ne devine pas le schéma, il le lit dans ce fichier.
Mettre à jour le contrat partagé si la forme exposée change.
Lancer `npm run db:migrate` sur la branche `dev`, puis `npm run typecheck`.
[/STEPS]

L'étape 4 est celle qu'on oublie, et son symptôme est déroutant : la colonne existe en base, la requête fonctionne, mais TypeScript prétend qu'elle n'existe pas. C'est normal — Kysely tire son typage de la déclaration, pas de la base.

[NOTE] Un usage de COMMENT ON COLUMN qui vaut d'être imité
La migration `0009` pose des commentaires SQL sur `garage_arrived_at` et `client_arrived_at`, parce que leurs noms datent du temps où un seul mode existait. En mode « je vais au garage », le garagiste n'« arrive » nulle part — il est déjà chez lui. Les renommer aurait coûté une contrainte SQL, un contrat partagé, quatre écrans et un registre, pour un gain de vocabulaire. La documentation vit donc dans la base, là où le prochain lecteur regardera.
[/NOTE]

#2 Les tests géospatiaux, et pourquoi ils sont ignorés par défaut

Vingt et un tests de l'interface de programmation exigent une véritable instance PostgreSQL avec son extension. Ni une base en mémoire ni SQLite ne savent exécuter `ST_DWithin`, et tester la requête centrale du produit contre une imitation ne prouverait rien.

Ces tests sont donc **ignorés** tant qu'une base de test n'est pas fournie :

[CODE]
TEST_DATABASE_URL=postgresql://… npm test --workspace @geocras/api
[/CODE]

[NOTE] Une branche dédiée, jamais dev, jamais main
La suite exécute `DROP SCHEMA public CASCADE` avant de reconstruire. Pointer cette variable sur votre branche de développement effacerait vos données de travail sans avertissement.
[/NOTE]

#2 Le test qui vérifie un plan d'exécution

Un test se distingue des autres : il ne vérifie pas un résultat mais la manière dont la base l'obtient. Il exige que la recherche de proximité passe par un parcours d'index géospatial et non par un parcours séquentiel.

C'est une exigence non fonctionnelle transformée en test, et c'est la seule manière d'empêcher une régression de performance de passer inaperçue. Un jour, quelqu'un réécrira cette requête « plus proprement » en mettant le calcul de distance dans le tri ; le résultat sera juste, les tests fonctionnels passeront, et la performance s'effondrera silencieusement. Celui-là échouera.

#2 Les scripts d'audit

[CODE]
npm run audit:arrivals       étalonne la preuve sur les données réelles
npm run report:commissions   relit le registre des commissions
[/CODE]

Le premier relit toutes les interventions terminées et compte deux erreurs. Les **faux négatifs** sont les demandes closes — donc une rencontre a bien eu lieu — dont la preuve n'atteint pas le seuil facturable ; c'est l'erreur coûteuse, celle qui fait fuir les garages honnêtes. Les **faux positifs** sont les demandes annulées dont la preuve serait facturable ; c'est l'erreur qui casse la confiance dans l'autre sens.

Il ne modifie rien. Il faut le relancer maintenant que les deux modes de service coexistent : les seuils ont été calibrés sur des dépanneuses, et rien ne dit encore qu'ils conviennent à des clients au volant.

#2 Les mises à jour à distance

Le module `src/updates/useOtaUpdate.ts` et le fichier `apps/mobile/OTA.md` couvrent la mise à jour du code JavaScript sans repasser par un magasin d'applications.

Le principe et sa limite tiennent en deux phrases. Ce qui est écrit en JavaScript — écrans, logique, libellés, styles — se met à jour à distance. Ce qui est natif — un nouveau module, une permission ajoutée, une version du kit de développement — exige une nouvelle construction et une nouvelle installation.

La conséquence pratique : ajouter une bibliothèque à modules natifs n'est jamais une mise à jour à distance, quoi qu'en dise le fait que l'installation se fasse par npm.
